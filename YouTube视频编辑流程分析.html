二、核心结论速览（TL;DR）

编辑不是「一个请求改完」，而是「提交 → 异步调度 → 轮询收敛 → 资源重建」四段式：
  1. ① 提交 → POST /youtubei/v1/video_editor/edit_video：带上编辑内容 + externalVideoId + baseVersion，服务端 1.74 秒返回 EDIT_EXECUTION_STATUS_SCHEDULED —— 只是「已排期」，什么都还没做。
  2. ② 轮询 → POST /youtubei/v1/video_editor/get_video_processing_status：每 ~3.5 秒一次，本次连打 59 次。
  3. ③ 收敛 → 第 59 次（t+218.1s）返回 EDITED 且 lastPublishedEditVersion 由 1 跳到 2，前端立即停止轮询。
  4. ④ 重建 → t+218.3s 起，编辑器全量重拉波形 / 信息卡 / 片尾 / 缩略图 / 新转码流。
抓包实证
⚠️ 最重要的一条：upload/feedback 对编辑流程「失灵」，全程谎报 100%。
  • 编辑期间 feedback 每 60.5 秒心跳一次，5 次全部返回 uploadStatus: SUCCESS、进度条 fractionCompleted: 1、文案「已处理 100%。」「视频已就绪」——而此时编辑根本没完成。
  • 上一篇《上传流程分析》里 feedback 是判断进度的主力；在编辑链路上照搬它会得到完全错误的结论。
  • 编辑进度的唯一可靠来源是 get_video_processing_status。
抓包实证
编辑复用上传期的标识，不产生新视频：
  • externalVideoId 全程不变（T6q1g5SPGps）——编辑是就地改动，不是「新建再替换」。
  • feedback 的 continuation 解出的 frontendUploadId 仍是上传时那一个（innertube_studio:1B2B34C9-…:0）——上传期标识被编辑期复用，直接衔接上一篇第五章。
  • 并发控制走 baseVersion 乐观锁：提交时报当前版本 "1"，成功后服务端版本变 "2"。
抓包实证

八、用 macro 拦截器自动化该链路

前置检查：当前 config/request-rules.json 里 sections.resends 与 sections.blocks 均为 false（分闸关闭），下面第 2、3 段配方生效前需要把对应分闸打开或删掉该键。record 支路独立于顶层 enabled，单独由 record.enabled 控制。

配方 1 · 复现本次抓包（只观测、不改写）

这就是本次用的配置，写下来便于复现。4 个端点的完整请求体 + 响应体会各落成独立文件到 dumps/，并生成可与时间线 join 的索引。

{
  "record": {
    "enabled": true,
    "urlPattern": "*",
    "includeBody": true,
    "saveBodies": [
      { "urlPattern": "https://studio.youtube.com/youtubei/v1/video_editor/edit_video?alt=json",
        "request": true, "response": true },
      { "urlPattern": "https://studio.youtube.com/youtubei/v1/video_editor/get_video_processing_status?alt=json",
        "request": true, "response": true },
      { "urlPattern": "https://studio.youtube.com/youtubei/v1/creator/get_creator_videos?alt=json",
        "request": true, "response": true },
      { "urlPattern": "https://studio.youtube.com/youtubei/v1/upload/feedback?alt=json",
        "request": true, "response": true }
    ]
  }
}

产物：timelines/timeline-replay-*.jsonl（全站被动记录）+ dumps/rec-*-{req,res}.json + dumps/rec-index-*.jsonl。索引行的 networkId 与时间线的 id 相同，可精确 join。

配方 2 · 被动捕获版本号（captures 支路）

把轮询响应里的 lastPublishedEditVersion 存进回放期变量池，供后续重发注入 baseVersion。不重发、不改响应，纯捕获。

{
  "captures": [
    {
      "_注": "轮询响应里拿当前已发布版本号，作下次编辑的 baseVersion",
      "urlPattern": "https://studio.youtube.com/youtubei/v1/video_editor/get_video_processing_status?alt=json",
      "extract": {
        "pubVersion": { "fromBody": "lastPublishedEditVersion" },
        "procStatus": { "fromBody": "videoProcessingStatus" }
      }
    }
  ]
}
变量池的生命周期是单次 runId，后到覆盖先到。因为轮询会打 59 次，pubVersion 会被反复覆写——这正是想要的：任何时刻读到的都是最新版本号。合理推断（机制见《拦截器规则配置手册》，本配方未实跑）

配方 3 · 编辑完成时自动触发下一步（resends + responseTrigger.when）

利用 when 表达式引擎在轮询响应变成 EDITED 的那一刻触发一次重发。下例演示「编辑完成后自动发起第二轮打码」，baseVersion 用配方 2 捕获的变量注入。

{
  "resends": [
    {
      "_注": "检测到 EDITED 后，用新版本号发起第二轮 blur 编辑",
      "urlPattern": "https://studio.youtube.com/youtubei/v1/video_editor/edit_video?alt=json",
      "setHeaders": { "x-macro": "edit2" },
      "set": {
        "baseVersion": "{{pubVersion}}",          # ← 配方 2 捕获的最新版本号
        "videoEdit": { "blurEdit": { "edit": { "blurRegions": [
          { "blurShape": "BLUR_SHAPE_RECTANGLE",
            "start": { "millis": -1 }, "end": { "millis": -1 },
            "trackedRegionCheckpoints": { "checkpoints": [
              { "rectangle": { "top": 0.1, "left": 0.1, "right": 0.3, "bottom": 0.3 },
                "timestamp": { "millis": 0 } } ] } }
        ] } } }
      },
      "responseTrigger": {
        "triggerUrl": "**/video_editor/get_video_processing_status*",
        "when": "hop == 0 && contains(text, 'VIDEO_PROCESSING_STATUS_EDITED')"
      },
      "dedupeMs": 600000                            # 10 分钟内只触发一次，防轮询重复命中
    }
  ]
}
三个必须注意的点：
  • hop == 0 不能省。 它保证只在真实响应上触发，从根上切断「重发又触发重发」的连环（maxResendHops 缺省 5 是熔断兜底，不是设计）。
  • dedupeMs 不能省。 编辑完成后前端可能还会补打几次轮询，每次响应都含 EDITED，不去重会触发多轮编辑。
  • baseVersion 必须用捕获值，不能写死。 服务端按乐观锁校验，用过期版本号提交预期会被拒。未验证（本次未实测版本冲突的错误码）
若只想「等编辑完成」而不重发，更轻的做法是只用配方 1 + 配方 2，然后在宏步骤里轮询变量池——或者干脆用 blocks 的 mode: "hold" 把 edit_video 挂起，在暂停模态框里人工确认参数后再放行。
