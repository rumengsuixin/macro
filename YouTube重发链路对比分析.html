一、一句话总览

录制的是上传 A.mp4 的原生三段式流程;3 条 resend 规则在 A 传完的瞬间自动「接力」再传一个 B.mp4。 时间线里因此并行两条轨道:蓝 = 浏览器真实发出的原请求、橙 = 工具注入的重发请求。 两条轨道请求几乎同形、响应完全等效,差异集中在少数被「提取→注入」改写的字段上。

三、触发链与「提取→注入」

三条规则形成一条 A→B→C 连环(hop 逐跳 +1),关键值全部从上一跳的响应头里提取,再注入下一跳:

# ① A 的 finalize 响应到达 → 点燃规则1 行47 id=8 响应 x-goog-upload-status: final │ 规则1.when: reqHeader('x-macro') != 1 && header('...upload-status')=='final' && reqHeader('...upload-command')=='upload, finalize' ▼ 行48 id=24 重发 upload/studio · start hop1 (+ x-macro:1) ── 新开一个上传会话 # ② 新会话的 active 响应 → 同时点燃规则2 和 规则3(都要求 req 带 x-macro:1) 行49 id=24 响应 x-goog-upload-status: active ├─ extract uploadUrl = 响应头 x-goog-upload-url → 注入 规则2 的 setUrl │ ▼ │ 行53 id=26 重发上传 …upload_id=oFMymQ9… hop2 body=B.mp4 26.5MB │ └─ extract scottyResourceId = 响应头 x-goog-upload-header-scotty-resource-id → 注入 规则3 的 set ▼ 行54 id=27 重发 createvideo hop2 resourceId.scottyResourceId.id = B 的值 # ③ B 的 finalize 响应也是 final,四个静态条件全中,本该再触发规则1…… 行76 id=26 响应 final 但该请求带 x-macro:1 → when 的 reqHeader('x-macro')!=1 = false → 断链,不传 C ✔
设计要点:x-macro 是「只补一个」的语义熔断 规则2/3 要求触发请求带 x-macro:1,所以它们只挂在重发出来的新会话(id=24)上,不会误挂到 A 的原生 active(id=3,行15)。 而规则1 的 when 里 reqHeader('x-macro')!=1 又亲手切断了「B 完成 → 再开 C」的无限连环。比单纯靠 maxResendHops:5 更精准。

规则3 的 set 只覆盖了顶层 resourceId,把 scottyResourceId 换成从 id=24 响应头提取的 B 视频资源 id;其余 30 个字段原样继承录制时 A 的值。

⚠️ 两个继承自 A 的字段值得警惕
  • title 仍是 "A" —— B 视频上传后标题会显示为「A」而非「B」,隐私(PRIVATE)、草稿态也全部继承 A。规则3 只换了底层视频资源,没碰任何元数据。若要 B 有自己的标题,需在规则3 的 set 里补 initialMetadata。
  • frontendUploadId 复用 A 的值 —— B 的 createvideo 用的是 (A 的 frontendUploadId, B 的 scottyResourceId) 混合配对。它返回 200 说明被接受,但若 YouTube 用它做去重,连传多个视频可能撞车。

六、系统性规律

重发请求 = 原请求的「改造复制品」,三处系统性差异:

  • ① 头必增不减:每个重发都加 x-macro-resend(值=hop 跳数:规则1=1,规则2/3=2)+ 用户配的 setHeaders;其余业务头(Authorization/CSRF/cookie)逐字继承,登录态不丢。
  • ② body 由工具重建:文件字节(replaceWithFile)/ 改参(set·append·remove)/ 原样三选一;而原请求的大 body 在回放 record 里往往是空的。
  • ③ URL/文件名仅按需改:只有配了 setUrl、x-goog-upload-file-name 之类的规则才改,其余逐字继承。
  • ④ 响应侧两者等效:三对的有效响应 status 与 x-goog-upload-status 完全一致——这正是「重发能冒充真实请求跑通」的证明。
