🔬 黑盒逆向分析方法论

从「网络边界」逆推内部处理步骤与逻辑 · 以 YouTube Studio 上传/删除为贯穿实例 · 目标无关、可复用

一、核心思想:站在网络边界上看

黑盒 = 拿不到目标系统的服务端源码,唯一能观测的是请求进 / 响应出这道网络边界。所谓「分析出内部步骤和逻辑」,本质是——

用边界上可见的三类信号,反推边界内不可见的资源模型与处理逻辑。
① 数据流
同一个标识/字段在不同请求之间如何流转:谁生成、谁引用谁、逐字是否相等。
② 时序
谁先谁后、各自耗时、响应时刻与依赖完成时刻的先后关系。
③ 状态变化
状态码(200/400/…)、响应体里的成功标志与实体变更(mutation)、前端界面随之出现的条目/进度。

下面 8 步就是把这三类信号系统性榨干的固定套路:先被动看清全貌,再主动扰动验证,最后诚实标注每条结论的证据强度。

二、方法论全景(8 步)

被动观测 · ① 取样(抓干净基线,不施扰动)
被动观测 · ② 时序重建 + 剥噪声(切出主链路 vs 辅助请求)
被动观测 · ③ 字段级逐字比对(追踪数据流 → 反推资源模型)
被动观测 · ④ 时序差推异步/因果(响应早于依赖完成 → 解耦)
证据升级 · ⑤ 响应体落盘(头/状态 < 正文)
证据升级 · ⑥ 令牌解码(base64 / URL-decode 撬内嵌结构)
主动测试 · ⑦ 扰动实验(控制变量:成对改 / 单改 → 反推校验规则)
交付纪律 · ⑧ 诚实标注证据边界(实测 / 推断 / 语义对应 分档)

① ~ ④ 只读不改,拿到「系统本来长什么样」;⑤ ~ ⑥ 把推测坐实为正文/结构证据;⑦ 才动手改输入看输出;⑧ 贯穿始终,给每条结论标价。

三、八步详解(每步配 YouTube 实例)

1

被动观测取样 —— 先拿一份干净基线

做什么
对一次完整业务操作(如「上传一个视频」),被动抓下它触发的全部网络请求,不改写任何一条。
怎么做
用「只记录不修改」的抓包支路(本项目 record 支路,走 CDP Network),被动全站观测。
铁律
第一遍绝不施加扰动——否则后面分不清「系统本来行为」还是「被我改出来的行为」。基线必须纯净。
YouTube 实例:一次上传抓到 117 条时间线(timeline-replay-20260716-115136713.jsonl),覆盖从选文件到草稿生成的全过程,总跨度约 66 秒。
2

时序重建 + 剥噪声 —— 从 100+ 条里剥出骨架

做什么
按时间戳排成时间线,把请求分成主链路(承载核心业务的少数关键请求)与辅助请求(轮询、埋点、静态资源等噪声)。
怎么做
按端点(URL)聚类计数、看请求体大小与响应耗时:耗时长/体积大/一次性的往往是主链路;高频重复的多是轮询噪声。
产出
识别出主链路 = 识别出内部处理的阶段划分。
YouTube 实例:117 条里剥出主链路仅 3 步——start(会话初始化)→ 字节上传 → createvideo(创建草稿);其余 ~114 条是 28 次 feedback 进度轮询、play.google.com/log 埋点、缩略图等噪声。
3

字段级逐字比对 —— 追踪数据流,反推资源模型

做什么
挑出关键标识,追踪它在各请求间的流转路径:首次出现在哪(请求体?响应头?)、后续在哪被引用、两处值是否逐字 === 相等。
怎么做
由「谁先出现、谁引用谁」推「谁生成」;由「逐字相等」推「同一实例被复用/绑定」;由「必须成对出现」推「校验规则」。
这是核心
服务端源码看不见,但数据流会出卖它的资源模型——这一步是从「外部数据」推「内部逻辑」的最强手段。

YouTube 实例:追踪两个标识的流转,逐字比对 ① 与 ③:

标识首次出现再次出现逐字比对推出
frontendUploadId① start 请求体③ createvideo 请求体前端生成、贯穿全程 → 配对键 + 幂等键
scottyResourceId① start 响应头③ createvideo 请求体服务端在 start 就分配、后被复用 → 已上传字节的资源句柄
结论:一次 start 产生一对 (fuid, scotty),原封不动带入 createvideo;createvideo 校验二者是否同源。——整套「资源槽位 + 配对」的内部模型,全是从边界上的字段流转反推出来的。
4

时序差推异步/因果 —— 用时间关系反推同步性

做什么
比较「某请求成功返回的时刻」与「它名义上依赖的操作完成的时刻」。若前者早于后者,说明二者异步解耦——该请求当场并不真的等依赖就位。
怎么做
按同一业务 id 配对请求/响应行,取响应时间戳做差;差值的正负号就是因果/同步性的证据。
威力
这类结论只能从时序看出,单看任何一条请求都发现不了。
YouTube 实例:createvideo 在 t+23.35s 就返回 200,而字节上传的 finalize 到 t+53.44s 才完成——早 30 秒。
推断:createvideo 当场不校验字节是否就位,只凭句柄 + 会话令牌即登记草稿;字节由后端异步收、异步转码(那 28 次 feedback 轮询就是在追这个进度)。⟹ createvideo 返回 200 ≠ 视频最终成功——验证是否真成,要看最终转码/可播放状态。
5

响应体落盘 —— 证据分级,别停在状态码

做什么
黑盒里证据有强弱:响应头 / 状态码 < 响应正文。能拿正文就别靠 200 猜语义。
怎么做
对关键端点单独抓完整请求/响应体(本项目 record.saveBodies,走 CDP Fetch 响应阶段 getResponseBody),落盘后逐字段读语义。
收益
把「凭 200 推测」升级为「有正文实证」,常能直接推翻先前的推断。
YouTube 实例:对 video/delete 抓到响应体后,发现 frameworkUpdates.entityBatchUpdate.mutations 只有一条 ENTITY_MUTATION_TYPE_DELETE、无 undoToken、success:true。
推翻旧假设:这确证是硬删除 / 实体层直接删除,而非此前凭 200 猜的「软删除 + 可撤销」。一条正文顶十条推测。
6

令牌解码 —— 撬开不透明 blob 里的内嵌结构

做什么
看似随机的长令牌 / key,往往内嵌明文结构。做 base64、URL-decode、protobuf 试解,常能撬出内部命名与主键。
怎么做
对 continuation token、entityKey、cursor 等不透明串逐层解码,匹配已知明文片段(如业务 id、实体名)。

YouTube 实例:

  • feedback 的 continuation → base64 解出含 innertube_studio 字样 → 证明轮询 token 内编码了 frontendUploadId(前端据此轮询「这一次上传」的进度)。
  • delete 响应的 entityKey → URL-decode + base64 解出 creator_video_data_<videoId> → 印证「实体层按 videoId 建主键」的存储模型。
解码把「黑盒里的随机串」变成「内部结构的自述」——是低成本、高回报的一步。
7

主动扰动实验 —— 控制变量,反推校验规则

做什么
前 6 步都是被动读;这一步才是真正的「测试」:改一个输入、看输出怎么变,由响应差异反推服务端的校验条件。
怎么做
用拦截器改写请求(本项目 rules 改 body / responseRules 改响应 / resends 改参重发),严格控制变量:每次只动一个字段。
读什么
状态码从 200 变 400、错误码文案(如 INVALID_ARGUMENT)、是否仍被接受——都是校验规则的指纹。

YouTube 实例(控制变量法):

扰动观测结果反推的内部规则
成对改 (fuid, scotty)请求仍有效安全令牌未对 body 整体签名锁定 → 改写这条路可行
只改其一(破坏配对)400 INVALID_ARGUMENT「二者必须同源」是硬约束
加密黑盒的突破口:当关键字段是密文(前端签名/加密),网络层只见密文。此时向页面主世界注入 hook(本项目 jsHooks)抓「明文入参 ↔ 密文出参 + 调用栈」,把加密黑盒也打开——扰动实验才能作用在明文上。
8

诚实标注证据边界 —— 给每条结论标价

黑盒推断能不能被信任,分水岭在于:把「实测 / 推断 / 语义对应」分开写,绝不把猜测当事实。每条结论都要标注它站在哪一档证据上。

证据档含义YouTube 实例
✅ 实测有正文 / 逐字比对 / 实跑扰动删除是硬删除(响应体 mutation 实证)
⟂ 推断由时序 / 间接信号合理推出,未直接验createvideo 异步不等字节(时序差 30s)
≈ 弱推断仅凭 content-length 等旁证,无正文删后重查响应变小 = 实体已消失
◻ 语义对应接口语义上成立,但非本次样本内闭环videoId = createvideo 产出(纯删除流里没抓到 create)
❓ 待验证已列为假设,需专门实验才能定同一对能否建多个 / 能否秒传 / blob TTL 多久
一份可信的黑盒报告 = 结论 + 每条结论的证据档。缺了后半截,再漂亮的结论也只是猜测。

四、方法论 ↔ 本项目工具链对应

对应步骤本项目支路 / 能力作用
① 被动观测record(CDP Network)被动全站抓时间线,拿干净基线,不改写
⑤ 证据升级record.saveBodies(CDP Fetch getResponseBody)关键端点请求/响应体落盘,头/状态 → 正文
⑦ 主动扰动rules / responseRules / resends改请求体 / 改响应 / 改参重发,控制变量做实验
⑦ 突破加密jsHooks(主世界注入)抓明文↔密文+调用栈,打开前端签名/加密黑盒

全字段速查见 拦截器规则配置手册.html;实例结果文档见 YouTube上传流程分析.html。

五、一页可复用 Checklist(逆向新目标时照走)

  • ☐ ① 对一次完整业务操作被动抓全量请求(不改),存一份干净基线时间线。
  • ☐ ② 按时间排序,按端点聚类计数,切出主链路 vs 噪声;主链路 = 内部阶段划分。
  • ☐ ③ 列出关键标识,逐个追踪:首现位置 → 再现位置 → 逐字比对;推出「谁生成/绑定/校验」。
  • ☐ ④ 对有依赖关系的请求算响应时间差;若 A 早于其依赖完成,标记「异步解耦」。
  • ☐ ⑤ 对每个关键端点抓响应体正文;凡「凭 200 猜的语义」都用正文复核一遍。
  • ☐ ⑥ 把不透明令牌 / key 做 base64 / URL-decode / protobuf 试解,找内嵌明文。
  • ☐ ⑦ 设计控制变量扰动:每次只改一个字段,记录 200/400 与错误码,反推校验规则;字段是密文则先注入 hook 抓明文。
  • ☐ ⑧ 每条结论标证据档(实测 / 推断 / 弱推断 / 语义对应 / 待验证);把「待验证」单列成下一轮实验。
一句话总结:被动抓全量 → 剥主链路 → 逐字追数据流 → 时序差推异步/因果 → 抓正文坐实 → 解码令牌撬结构 → 控制变量做扰动 → 每条结论标证据强度。
